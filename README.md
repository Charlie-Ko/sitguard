# SitGuard · 桌面久坐提醒器

放在办公桌上的一块 135×240 小屏。数你坐了多久，到点整屏变红喊你起身；
拿起来摇三下，它就清零重新数。其余时间黑屏，一声不响。

**硬件**：M5Stack StickS3（K150，ESP32-S3-PICO-1-N8R8 / 8MB Flash + 8MB PSRAM）
**定位**：纯本地设备，不联网、不连云。与「会议记录桌面机器人」是独立项目。

功能规格见 [SPEC.md](SPEC.md)，决策与路线见 [project.md](project.md)。

---

## 零、v0.2 形态变更（重要）

**v0.1 是挂脖穿戴，v0.2 改成桌面摆放。** 因此：

| 删除 | 原因 |
|---|---|
| 姿态角 `asin(az/\|a\|)`、坐正标定、零点 | 不佩戴，躯干倾角测不出来 |
| 姿态条、绿/黄/红三态、塌腰 45 秒判定 | 同上 |
| 灵敏度设置、标定页、充电页 | 只服务姿态判定 / 用户不要 |

IMU 保留，但只做两件事：**判断被拿起来了**、**判断被摇了三下**。详见第四节。

## 一、编译与烧录

**推荐用一键脚本**（已封装 touch → 烧录 → 复位 → 读日志的全流程）：

```bash
cd firmware/SitGuard
./flash.sh                 # 编译 + 烧录 + 复位 + 打印 8 秒串口日志
./flash.sh --full-erase    # 想清空一切时用（擦全片，会连 bootloader 一起重烧）
```

手动命令（不推荐，会被下面的 USB-JTAG 坑绊住）：

```bash
pio run                            # 编译
pio run -t upload                  # 烧录（需先 1200bps touch）
```

> 这台机器装了多套 Python，`pio` 也有多份。`flash.sh` 里用的是绝对路径，
> 避免 shell 的 PATH 顺序不同导致「终端里能编译、Agent 里不能」。

### 依赖库

需要两个库，**版本要卡住**（新版改过 API）：

| 库 | 版本 | 用途 |
|---|---|---|
| M5Unified | 0.2.26 | StickS3 板型探测、BMI270 六轴驱动、电源管理 |
| M5GFX | 0.2.33 | 屏幕驱动、`efontCN` 中文字库 |

**新机器 clone 后**，跑一次：

```bash
bash tools/setup_libs.sh
```

它把两个库按 tag 拉到项目根的 `libs/` —— `platformio.ini` 里的 `lib_extra_dirs` 正指向那里。
也可以从 PlatformIO registry 装：

```bash
pio pkg install -l "m5stack/M5Unified@0.2.26" --no-save
pio pkg install -l "m5stack/M5GFX@0.2.33" --no-save
```

`libs/` 不进仓库 —— M5GFX 单独就有 152MB，而且它是能重新拉下来的。

### 板型说明
PlatformIO 的 espressif32 平台**没有** `m5stack-sticks3.json`，所以 `platformio.ini` 用
`board = esp32-s3-devkitc-1` + `board_build.arduino.memory_type = qio_opi`。M5Unified 启动时
自行探测出 `board_M5StickS3`，屏幕、BMI270、按键（BtnA=G11 / BtnB=G12）都按 StickS3 初始化。

**自检方法**：开机串口应打印
```
[SitGuard] board=26 (StickS3=1) screen=135x240
[cfg] nvs ver=2 (want 2)
[cfg] sound=0 limit=45 bright=1
[SitGuard] imu enabled=1
```
`StickS3=0` 说明板型没认出来，屏幕/IMU 参数会不对。

**体积**：Flash 54.9%（1.83MB / 3.34MB），RAM 14.6%。比 v0.1 涨了 17 个百分点，
主要是 `efontCN_24` 中文字库（提醒页大字）；不想占这么多可以退回 `efontCN_16`。

## 二、烧录踩坑（已解决，记录原理）

### `Could not configure port: (6, 'Device not configured')`
**根因**：StickS3 用 ESP32-S3 原生 USB-Serial-JTAG。esptool 默认 `--before default_reset`，
打开端口后发复位信号，USB 会**断开重新枚举**；macOS 重建 `/dev/cu.usbmodem*` 节点的速度
跟不上 esptool 的重试。**这不是线的问题，也不是驱动问题，重试多少次都一样。**

**正确姿势（`flash.sh` 已封装）**：
1. `1200bps touch` 让芯片自己进 ROM 下载模式（pyserial 开 1200 波特→`dtr=False/rts=True`→关）；
2. 用 `--before no_reset` 连（`platformio.ini` 里 `upload_flags` 已设），不要再复位；
3. 烧完再 touch 一次退出下载模式，等 4 秒启动。

### 烧完设备不启动、PID 变成 303A:0009
`--after hard_reset` 靠 RTS 引脚复位，USB-JTAG 上的 RTS 是虚拟信号，拉不动芯片，
设备就留在 bootloader 里。同上，靠第二次 touch 解决。

### 判断设备处在哪
| PID | 含义 |
|---|---|
| `303A:0009` | ROM 下载模式（等着被烧） |
| `303A:1001` | USB-Serial-JTAG 正常工作 |
| `303A:8120` | 其他固件（如 UiFlow）的 CDC |

### NVS 脏数据清不掉
`erase_flash` / `erase_region` 在 USB-JTAG 下偶发不生效。已在代码里做了兜底：`config.h` 的
**`CFG_VERSION`** 与 NVS 里存的版本不一致时，启动自动 `clear()` 整个 `sg` 命名空间。
改了设置项结构或算法语义，就把这个数字 +1。串口打印 `[cfg] nvs ver=N (want M)`。

### `i2s_driver_uninstall(): I2S port 0 has not installed`
启动时多一条 E 级日志。原因是在 speaker 从未 `begin()` 的情况下调了 `M5.Speaker.end()`，
M5Unified 会去卸载一个不存在的 I2S 端口。**已经去掉这个多余调用**——`M5.begin()` 只填配置、
不启动 I2S，功放本来就是关的，不需要额外 end。

### PSRAM 分配失败 / 屏幕花屏
`board_build.arduino.memory_type = qio_opi` 别改。StickS3 是 8MB Flash + 8MB **OPI** PSRAM，
写成 `qio_qspi` 会认不出 PSRAM。`M5Canvas` 要 135×240×2 = 64KB，必须走 PSRAM。

## 三、按键

正面两个物理键：**KEY1 = G11（BtnA）**、**KEY2 = G12（BtnB）**。机身侧边还有一颗
**电源/复位键（PWR）**，它不是 GPIO，走 M5PM1 的 PEK 通道，固件读不到也改不了。

### 侧边电源键（见官方文档 core/StickS3「按键操作说明」）

| 操作 | 结果 | 谁在管 |
|---|---|---|
| **单击** | 开机 / **复位重启**（开机状态下单击就是重启） | M5PM1 硬件 |
| **双击** | **关机**（切电，不是休眠） | M5PM1 硬件 |
| **长按** | 进入下载模式（绿色 LED 闪） | M5PM1 硬件 |

**要关机就双击这颗侧键**，不用插拔 USB、不用烧固件。

> **关机 / 复位会清掉久坐计时。** 侧键关机是 PM1 直接切电，MCU 没有执行任何清理代码的机会；
> 单击复位更是直接重启。久坐时长、今日累计、最长连续、起身次数都在 RAM 里，一断就没。
> **设置（声音/间隔/亮度/屏保）存在 NVS，不受影响** —— 也不会触发 `CFG_VERSION` 自清，
> 因为版本号没变。如果以后要给「今日累计」跨重启保留，得单独写 NVS，且要处理掉电时机。

**短按 KEY1 循环翻页**：主界面 → 详情 → 姿势 → 番茄 → 主界面。

| 状态 | KEY1 短按 | KEY1 长按 1.5s | KEY2 短按 | KEY2 长按 1.5s |
|---|---|---|---|---|
| 屏保中 | 退出屏保¹ | 退出屏保¹ | 退出屏保¹ | 退出屏保¹ |
| 黑屏 | 亮屏 6 秒 | 亮屏 6 秒 | 亮屏 6 秒 | 亮屏 6 秒 |
| 主界面 / 详情 / 姿势 | 下一页 | **进设置** | **声音开关** | 进设置 |
| 番茄页（空闲） | 下一页 | 进设置 | **开始专注（自动进全屏）** | 放弃 |
| 番茄页（运行中） | **进全屏** | 进设置 | 暂停/继续 | 放弃 |
| 番茄全屏 | **退出全屏** | 进设置 | 暂停/继续 | 放弃 |
| 提醒页 | **我起来了（清零）** | 稍后 5 分钟 | 我起来了（清零） | 稍后 5 分钟 |
| 设置页 | 下一项 | **退出设置** | 改当前项的值 | 退出设置 |

> **v0.5.1：KEY2 在主界面 / 详情 / 姿势三页改成了声音开关。** 以前这页 KEY2 和 KEY1 干的是
> 同一件事（都翻页），按下去毫无意义。现在它是个真正的一键静音：切换后主界面底部显示
> 1.6 秒「声音 开 / 声音 关」，打开时还会先滴一声确认，顶栏左侧出现黄色 `M` 表示静音。
> 开关走 NVS，重启保持。设置页里的「声音」项仍然保留，两条路径结果一致。

**核心交互只有一个：摇三下 = 我起来了。** 摇动时屏幕底部显示 ●●○ 三个圆点，数到几下看得见，
不会出现「摇了没反应」的错觉。

> ¹ 屏保期间若久坐已到点（卡片已转红），退出屏保会顺带把提醒页交出来。

> **摇三下的生效范围（v0.5.5）**：主界面、提醒页（「起身走走」红屏）。
> 详情 / 姿势 / 番茄 / 设置 / 番茄全屏摇动一律不重置（串口打印 `[shake] ignored scr=N`）。
> 屏保里分两种：没在报警只叫醒；卡片已经红了（`alertUnacked`）摇三下直接清零。
>
> 起因是作者在姿势页看角度时晃了两下把久坐清零了 —— `takeShake()` 原来无条件调
> `doReset()`，是真 bug。v0.5 收紧门禁时收过头，把提醒页也误伤了：
> 那一页上明明印着「摇三下 重新计时」，摇了却没反应。v0.5.5 修回来了。

## 四、检测算法（v0.2 全部逻辑）

### 4.1 静止与桌面基准
```
motion = EMA(| |a| − 1g |, 0.05)
静止   = motion < 0.03g
```
连续静止 **3 秒** → 把当前重力单位向量记为**桌面基准**。基准持续跟随，设备被挪到新位置
3 秒即自适应，不会一直报「被拿起」。

### 4.2 拿起唤醒
```
tilt  = acos( dot(当前单位重力向量, 基准) ) × 180/π
拿起  = tilt > 20° 且 motion > 0.10g
```
**为什么要两个条件**：打字、敲桌子的震动会让 motion 短暂飙高，但不改变设备朝向；
一旦被拿起来，姿态必然变化。两者同时满足才判「拿起」，误判率才压得下来。

### 4.3 摇三下重置（三重约束，缺一不可）
```
① tilt > 12°        设备已离开桌面 —— 排掉敲桌子、插 USB 的冲击
② | |a| − 1g | > 0.55g，相邻峰值间隔 ≥ 300ms   —— 一次摇动的加速峰/减速谷合成一个
③ 3 个峰值跨越 ≥ 600ms                        —— 撞击余震凑不齐，真摇三下才凑得齐
```
峰值阈值 0.55g 的依据：手持摇晃轻松超过 1.5g，键盘震动传到设备通常 < 0.3g，区分度足够。

**触发范围**：主界面 + 提醒页 → 清零；**迷宫页 → 换一张随机地图**（不清久坐计时）；
其余页面只消费事件、不动作。
屏保中摇动 = 退出屏保，不清零。

> **踩坑记录**：最初只用了 ①阈值 0.45g + ②250ms 去抖，结果插拔 USB 的撞击直接触发了
> 两次误重置。加上「姿态必须离开桌面」和「3 下必须跨越 600ms」两条才稳。

### 4.4 计时
`millis()` 差值累加，单次差值 > 10 秒视为异常丢弃（防极端卡顿跳变）。uint32 减法天然处理溢出。

## 五、省电

| 档位 | 触发 | 动作 | 估计电流 |
|---|---|---|---|
| ACTIVE | 按键 / 拿起 / 提醒 / 设置 | 屏亮、50Hz 采样、CPU 240MHz | ~50mA |
| SLEEP_SCREEN | 6 秒无操作 | 背光归零（L3B 关）、25Hz 采样、CPU 80MHz | ~20mA |

**为什么不做深睡**：桌面设备必须随时能感知「被拿起」和「被摇三下」。深睡要靠 BMI270 的
AnyMotion 中断唤醒，而该中断只报「有动静」、不能上报具体波形——**摇晃计数就没法做了**。
为了摇三下这个核心交互，放弃深睡的 14 天续航，换 20mA 常驻。

桌面场景建议**插着 USB 用**，250mAh 只是断电兜底。

### 5.1 为什么插着 USB 也「充不满」

**先说结论：充电没坏。是「屏保常亮时的耗电 ≈ 充电电流」，净电流接近零，所以电压不涨。**

M5PM1 这颗电源芯片**没有库仑计**：既没有充电电流寄存器，也没有充电状态寄存器。
库里的 `setChargeCurrent()` / `setChargeVoltage()` / `isCharging()` / `getChargeCurrent()`
全是直接返回 `false` / `0` 的空壳。**能读的只有 VBAT 和 VIN 两个电压。**

所以判断「充没充电」只能看电压趋势，不能看瞬时值。

实测（v0.6.0，串口每秒的心跳日志里带 `vb=`）：

| 状态 | 采样 | VBAT 变化 |
|---|---|---|
| 屏保常亮（久坐横屏） | 12 次 × 15 秒 = 3 分钟 | 3956–3984mV 抖动，**净 −2mV ≈ 0** |
| 熄屏 | 桌面微振动被 IMU 判成「拿起」，屏幕自己又亮了，**这一组没测成** | — |

**屏保状态 3 分钟净变化为零**，说明充电电流和负载电流基本打平 —— 这就是「充不满」的真相：
不是充不进去，是充多少用多少，电压停在原地。

同一时段另一个观察：VBAT 从 3946mV 一路涨到 4012mV，那是在反复烧录重启、
屏幕时亮时灭的几十分钟里发生的。**屏幕一关，净电流立刻转正。** 方向是明确的。

> ⚠️ 上一版这里写的「GPIO2 = CHG_STAT，改成 input 才读得到真话」是**错的**，
> 已在 v0.6.0 推翻。**PM1 的 GPIO2 是 LCD 电源闸（L3B Enable）**，把它设成 input
> 会让屏幕直接黑掉，而系统照常跑、串口心跳一切正常 —— 我为此浪费了半天。
> 真正的注释就写在 M5GFX 源码里：`// PM1_G2 -- L3B Enable, LCD Power On`。
> 现在 `setup()` 每次都会调 `lcdPowerOn()` 把闸合上，串口 `n` 可随时急救。

**电量百分比的算法**（M5Unified 源码）：

```
level = (mV - 3300) × 100 / (4150 - 3350)     即 (mV - 3300) / 8
```

**这是一个纯线性映射，而锂电池的放电曲线根本不是线性的**：中间 30%–80% 那一段
电压几乎是平的（每 1% 只有 4.8mV），两端才陡（每 1% 有 11–15mV）。
后果是中段误差最大：

| 电压 | 真实电量 | 算法显示 | 偏差 |
|---|---|---|---|
| 3.74V | 30% | 55% | **+25** |
| 3.82V | 50% | 65% | +15 |
| 3.98V | 80% | 85% | +5 |

**低电量段最危险**：显示 55% 实际只剩 30%，再撑一会儿就关机。
另外充电时读到的电压里还叠着内阻压降（I×R），比真实开路电压偏高几十 mV，
所以充电中的百分比还要再虚一点。

**没有更好的办法**：真要精确只能上库仑计（电流积分），而 PM1 没有。
能做的只有分段查表 + 充电时补偿，或者干脆只显示 5 档文字。
日常插着用不必纠结那个百分比 —— 对「一直插着电的桌面设备」，80% 和 100% 没有区别。

> 另外 GPIO3 = CHG_PROG 是充电电流档位选择（M5 官方文档：低电平 = 大电流，浮空 = 小电流），
> 上电默认是 output 低，也就是大电流档。对 250mAh 的电池来说这一档偏激进，
> 但实测换到小电流档并不改变「充不满」的结果，所以没有动它。
> **注意：动 GPIO3 只能动 bit3 —— bit2 是 LCD 电源闸，碰一下就黑屏。**

> **为什么从「时间表 + loop 轮询」改成 PCM**：轮询节拍受主循环约束。实测第四拍比理论晚
> 0 / 11 / 20ms（`draw()` 一次 `pushSprite` 就是 13ms，正好卡在两拍之间），而 20ms 正是
> 人耳能听出节奏不齐的量级。PCM 进了 DMA 之后节拍由硬件采样时钟决定，主循环再卡也不影响。
> 顺带每声首尾加 2ms 淡入淡出，消掉 `tone()` 硬起停的咔哒。
>
> 采样率 35200 = 2200 × 16，和 M5Unified `tone()` 内部一致（它也是每周期 16 点），音色不变。
> buffer 放**内部 RAM**：I2S DMA 反复读它，走 PSRAM 要过 cache，音频这种小数据量没必要冒险。

### v0.5.3 增量：屏保第 4 种模式「久坐」

## 七、两个硬坑（v0.4 遇到，v0.5 处理完）

### 1. `M5.Rtc` 在 StickS3 上会直接崩 → 屏保「时钟」已删除

板上**没有 RTC 芯片**（M5PM1 无时钟寄存器，也没挂 PCF8563/BM8563）。更糟的是 M5Unified 的
`RTC_Class` 在 board 不匹配时 instance 是空指针，调 `M5.Rtc.begin()` 直接
`Guru Meditation / LoadProhibited`：

```
Guru Meditation Error: Core 1 panic'ed (LoadProhibited)
A3 : 0x00000051        ← 0x51 就是 PCF8563 的 I2C 地址
EXCVADDR: 0x00000000
```

v0.4 绕开 API 用开机计时（uptime）顶替，但**一个显示 03:15、手机是 19:15 的「时钟」不是屏保，是误导**。
v0.5 直接删掉这个模式（`clock.h` 已归档到 `deprecated/`），屏保只剩贪吃蛇与呼吸。
想要真实时间只能联网 NTP，那是另一件事。

### 2. `M5.Power.isCharging()` 对这块板永远返回 false

`M5PM1_Class::isCharging()` 是硬编码 `return false` 的桩实现。判断插没插 USB 必须直接读
PM1 的 `PWR_SRC(0x04)`：

```cpp
uint8_t v = M5.In_I2C.readRegister8(0x6E, 0x04, 100000);
bool usb  = (v & 0x01) != 0;      // bit0 = 5VIN valid
```

读回全 `0x00` 或全 `0xFF` 视为 I2C 失败并保持上次判断 —— 否则一次误判为「充电中」
就会让屏保常亮把电池耗干。

### 8.2 屏幕全黑事故：PM1 的 GPIO2 是 LCD 电源闸

**这是本项目代价最大的一次踩坑，记下来防止再犯。**

v0.5.5 为了读「充电状态」，把 PM1 的 `GPIO_MODE(0x10)` bit2 清成 input。
结果**整块屏直接黑掉**，而系统照常跑、串口每秒心跳、画布里有 422 个白像素、
`setBrightness(255)` 回读也是 255 —— 软件层看到的一切都是好的。

真相在 M5GFX 源码里写着：

```c
// PM1_G2 -- L3B Enable, LCD Power On (M5Stack PM1 G2)
bitOff(0x16, 1<<2);   // 选 GPIO 功能
bitOn (0x10, 1<<2);   // output
bitOff(0x13, 1<<2);   // push-pull
bitOn (0x11, 1<<2);   // 输出高 → LCD 上电
```

**GPIO2 从来不是 CHG_STAT。** 那四步缺一不可，而且 PM1 带电池时常电、复位不复位，
写坏了会一直坏到重新点一次。

- 修复：`lcdPowerOn()` 在 `setup()` 每次重放四步；串口 `n` 随时急救；
  `k` 改为只读显示 `LCD(G2) -> ON|OFF`。
- 顺带改正：`PM1_GPIO_PUPD0` 原来写的 `0x14` 是错的，M5GFX 用的是 `0x13`。

**教训**：改任何外设寄存器前，先去库源码里搜这个寄存器的用途，
别靠「读值反推语义」。我用一个 0/1 的变化说圆了自己编的故事，绕了两天才发现。

## 九、v0.8 增量：BLE 体感手柄 + 浏览器打砖块

主界面 → 详情 → 姿势 → 番茄 → 迷宫 → **手柄** → 主界面。

设备翻到第 6 页（横屏）后开始广播，浏览器里的打砖块连上来，倾斜设备就能左右移动挡板。

### 9.1 为什么走「自定义 GATT」而不是 BLE HID

这是整个功能最关键的一个选型，走错了整件事做不成：

| 方案 | 浏览器能拿到数据吗 |
|---|---|
| BLE HID（标准手柄） | **不能**。配对后归操作系统管，Gamepad API 只认有线或系统已映射的手柄；WebHID 只支持有线 USB 和部分蓝牙经典设备 |
| 自定义 GATT + Web Bluetooth | **能**。可以订阅任意特征 |

所以固件里定义了一个私有 service，网页用 `navigator.bluetooth.requestDevice()` 连上来
订阅 notify。前提：`optionalServices` 里要写这个 UUID，否则 `getPrimaryService` 直接报错。

### 9.2 协议：只发原始加速度，不发角度

11 字节一包，50Hz：

```
A5 | seq | ax(i16) | ay(i16) | az(i16) | btn | bat | sum
```

**角度换算放在网页里做，不放在固件里。** 理由是一条踩过的坑：

StickS3 的 IMU 被 M5Unified 做了轴重映射（`axis_order_yxz | axis_invert_y`），
哪根轴对应「左右」只有拿在手上才知道。迷宫那次为了一个正负号烧了三版固件 ——
先 `+a`（球往上飘），再两轴 `-a`（上下反），最后只给 x 取反才过。

同样的坑这次用协议设计绕开：固件只负责如实报三轴，解释权在浏览器。
改一行刷新页面就能试，不用烧录。

### 9.3 轴自动识别：不猜握法

横过来以后屏幕的「左右」在设备坐标系里是 **y 轴**（竖屏时才是 x 轴）。
但「横过来」本身就有很多种握法 —— 立着、平托、斜靠，重力落在哪个轴上完全不同。

所以网页端做了一个 2.5 秒的学习窗口：

1. 连上后提示「左右晃一晃手柄」
2. 期间记录三轴的 min/max
3. 选变化幅度最大的那根当左右轴，零点取该轴中值
4. 之后锁定；按 `R` 可以重来，按 `1`/`2`/`3` 手动指定

用户完全不需要知道「轴」是什么。

### 9.4 零点校准：绝对角度没有意义

第一版把绝对倾角直接映射成挡板位置，实测一进页 `tilt` 就顶到 ±1.00 满偏。
原因是设备当时是**竖着立**的（`a=(0.99, 0.02, -0.01)g`，重力落在 x 轴），
`atan2(ax, az)` 算出来 91°，直接打满。

同一台设备，立着、斜靠、托在腿上，同一个「歪 10°」对应完全不同的手腕动作。
**只有相对刚握住的姿态的偏移量才是用户想要的。** 所以进页后前 600ms 持续
跟踪当前姿态当零点（用户往往进页后才把手摆好），之后锁定。

### 9.5 用重力分量，不用 atan2

设备立着时 `az ≈ 0`，`atan2(ax, az)` 的分母趋零，角度会剧烈跳变。
直接取重力在该轴上的分量（单位 g）就没有这个问题 —— 它本身就是
「重力有多少落在屏幕左右方向上」，物理意义干净，也不受另一轴姿态影响。

满偏定在 `0.5g`，约等于手腕倾斜 30°，手不离桌的自然行程。

### 9.6 资源代价

| 项 | 变化 |
|---|---|
| Flash | 56% → **72.9%**（Bluedroid 协议栈约 570KB） |
| 静态 RAM | **21.3%**（69.7KB / 320KB），几乎没变 |
| 运行时堆 | `BLEDevice::init()` 吃掉约 **62KB**（247KB → 185KB） |

**惰性初始化、不 deinit。** `init()` 要 60–80ms 且吃 62KB 堆，所以只在第一次进
手柄页时做。离开只「停广播 + 断开」，**不调 `deinit(true)`** —— Arduino-ESP32 的
deinit 有已知崩溃面，而我们要的只是「不用时安静」，协议栈空转的电流跟反复初始化
失败的风险比，完全不值得。

进屏保、进提醒页、进设置页都会 `padRelease()`，不会出现「在设置页里还连着蓝牙」这种事。

不是「歪了几度」，看设备 = 看游戏，不用换算。

顶部状态点（灰=断开 / 黄=广播中 / 绿=已连接），右上角还有一个**数据流小点**，
每发一包闪一下。这个不是装饰：连上了但网页收不到数据，是这套方案最可能出的问题
（CCCD 没订阅、页面没调 `startNotifications`），有点在闪就说明设备在发。

## 十、v0.8.1 / v0.8.2：从「歪」改成「挥」

作者上手玩了一轮，反馈五条：连接提示挡画面、掉球震屏、发球有滴声、
竖着握方向不对、以及最要命的一条 —— **「我要的是左右摆动，不是左右倾斜」**。

前四条是手感打磨，第五条是整个输入模型的换血。

### 10.1 前四条（都是小刀）

| 问题 | 原因 | 改法 |
|---|---|---|
| 「已连接」压住挡板 | 连接面板是 HTML 定位在 `bottom:22px`，成功后 2.6 秒又弹回来，正好落在挡板（画布 y=706）那条横带上 | 面板整块删掉，改成**画在画布上**的「连接手柄」胶囊，位置在砖块和球之间的空地；连上就不再画 |
| 掉球震屏 | `loseBall()` 里 `G.shake = 9`，整屏 ±9px 抖 | 删掉，换成屏幕下沿一条淡红渐变。抖的时候挡板也跟着晃，人只会更慌 |
| 发球有「滴」 | 固件 `SCR_PAD` 的 KEY2 分支调了 `beepOk()` | 删掉。一局按十几次，每按一次滴一声像在按电梯 |
| 竖着握方向不对 | 手柄页是**横屏**，人却竖着拿 —— 手上一个方向、屏幕上一个方向 | 手柄页改竖屏 135×240 重排；倾斜量改算**屏幕平面里的侧倾角**，不再挑单轴 |

顺带修了两个布局 bug：「已连接」那一条之外，窗口比 3:5 窄时画布会被纵向拉伸 7%
（`height:100vh` + `max-width:100vw` 把比例撑破了），换成 `width:min(100vw,60vh)`。

### 10.2 第五条：为什么「倾斜」和「摆动」是两件事

- **倾斜**读的是**姿态** —— 重力方向。加速度计直接就能测，绝对、不漂。
- **摆动**读的是**位移** —— 手在空间里平移。加速度计要两次积分才能得到位移，
  两次积分必漂。

所以第一版把「摆动」硬套在加速度计上，注定要翻车，而且翻车的方式很隐蔽：

```
只靠加速度计，歪 10° 并保持  →  挡板甩出去 150px
只靠加速度计，真挥一把        →  挡板只动 29px
```

方向都对，比例正好是反的。根因是物理层面的：**加速度计分不清「举着歪住」和
「持续横向加速」—— 这就是爱因斯坦的电梯，读数完全一样。** 用手算、调参数都
救不回来，只能加传感器。

### 10.3 解法：加陀螺仪，做互补滤波

协议从 11 字节扩到 17 字节（`gx/gy/gz`，int16，0.1°/s），网页端：

1. **互补滤波**维护重力方向 `gh`（Mahony 一路）：陀螺推进 `d(gh)/dt = −ω × gh`，
   加速度慢修正（`AHRS_KP=0.5`，2 秒时间常数）只治零偏。
2. **加速度门控**：只有 `|f| ≈ 1g` 时才让加速度修正。挥手时 `|f|` 偏离 1g，
   此时加速度计的方向是「重力 + 手的加速度」的合成，拿它修正等于把挥手当成姿态变化。
   **这一步不做，挥完手会残留一个反方向的速度，挡板自己往回滑。**
3. **线性加速度** `= f − gh`，即 Android 的 `TYPE_LINEAR_ACCELERATION`。
4. 积成速度再泄漏（τ=0.30s），挡板位移 = 速度 × 增益。
   增益的量纲是「手移 1 米 = 多少像素」，默认 1700（横穿全屏约挥手 28cm）。

改完同一组动作：**挥一把 197px，歪 10° 并保持 0.7px。**

### 10.4 两个踩过的坑

1. **给速度加死区 = 积分器永远爬不起来。** 速度是加速度的积分，轻挥一个包只加
   0.01m/s，一进死区就被清零 —— 表现是「轻轻挥完全没反应」。
   死区只能加在加速度上。这是跑数值测试才发现的，手感上根本看不出来。
2. **增益按「一挥 3cm」标定，差了 10 倍。** 挡板位移 = 手位移 × 增益，
   第一版取 650 意味着手要移 74cm 才能横穿屏幕，实测挥幅 20~30cm。
   现在 1700，并且 `[` `]` 可以现场 ±15% 调、存 localStorage。

### 10.5 验证

`tools/test_tilt.js` —— 把页面里的 `<script>` 抽出来，用桩件挡掉渲染，
喂合成的加速度/角速度包，检查数值：

## 十一、v0.9：从「挥」改成「转」——一次算法族的更换

作者的反馈只有一句：「很难精准控制。」这句话值一次重做，因为这不是调参能解决的。

### 11.1 先把方向搞对：我去查了成熟方案

空中鼠标这个品类做了二十年，结论是**统一的**：

> **角速度 → 指针速度（rate control），不要积分。**
> 有算法会试图通过加速度积分获取位移 —— **但这种算法肯定是不行的，
> 因为传感器的精度限制会非常不准确，基本没有解决的可能性。**

我 v0.8.2 做的恰好是被否掉的那条：线性加速度积成速度再积成位移。所以
「很难精准」不是灵敏度的锅，是算法族选错了。位移类（position control）误差随
时间平方增长，这是 dead reckoning 的教科书结论，不是我调不好。

标准链路（空鼠、DS4Windows、Steam Input、飞智体感，四家写法不同、顺序一致）：

```
陀螺 → 减零偏 → 死区(5~10%) → 指数/S 曲线 → 低通 → 速度
```

### 11.2 一个和握法无关的解法：`yaw = −(ω · ĝ)`

横握之后第一个问题就是「哪根轴是左右」。这次不猜了。

加速度计静止时读的就是「上」，把它归一化成 `ĝ`；陀螺的角速度矢量 `ω` 和 `ĝ`
点乘，得到的就是**绕世界竖直轴的转动分量**。竖握、横握、斜着捏、躺着玩，
左右挥永远是同一个符号 —— 因为 `ω·ĝ` 问的不是「哪根轴」，而是「绕竖直转多快」。

这也顺手解决了空鼠资料里的「运动平面不匹配」：设备一歪，同样的动作会划出斜线，
正解就是拿加速度测倾角做融合，而不是硬挑一根轴。

正交性实测（数值测试第 [11] 段）：抬腕 180°/s 持续 0.4 秒，挡板位移 **0.00px**。
这就是点积的看家本事 —— 上下抬、前后点、绕屏幕转圈，全被投到零。

### 11.3 三个必须做对的细节

1. **零偏要运行时学，不是出厂标一次。**
   MEMS 陀螺零偏随温度漂，静止判据 `|ω|<14°/s` 且 `||f|−1|<0.1g` 连续 120ms，
   此时以 τ=0.6s 慢学。测试里注入恒定 +7°/s 零偏，1.2 秒后被吃到 6.1，
   挡板位移 0.0px。
2. **死区加在角速度上，不是速度上。**
   v0.8.2 的坑是给积分后的速度加死区，会把积分器按死在零位（轻挥永远没反应）。
   现在死区在「手转多快」这一级，挖掉 ±9°/s 再把剩余拉回 0，过死区不突跳。
3. **expo 压中心。** `y = 0.45x + 0.55x³`。30°/s 的输出只有 150°/s 的 14%
   —— 微调精度全在这个曲线里，线性映射必然「要么不动要么窜」。

### 11.4 手感参数换了量纲

以前是 `SW_GAIN = 1700`（手移 1 米对应多少像素），现在是
`RATE_SPAN = 0.55s`（满偏时从最左到最右用几秒）。后者能直接和直觉对账：
「我甩到底，板半秒走完全屏」。按 `[` `]` 调，存 localStorage。

### 11.5 不再靠猜：动作录制 + 离线分析

按 `O` 开始录，做几下动作，再按 `O` → 自动下载 19 列 CSV（原始 6 轴、融合后的
重力方向、学到的零偏、每一级中间量、挡板位置）。然后：

```

```

它回答五个问题，每个都直接对应一个参数：

| 输出 | 对应参数 |
|---|---|
| 静止段零偏 + 3σ | `YAW_DEAD` |
| 「绕竖直转」占比 | **该用 rate 还是 swing**（占比 <35% 说明你在平移手臂，rate 吃不到） |
| `yaw` 的 p99 | `YAW_FULL` |
| yaw→板速互相关滞后 | `OE_FC_MIN`（>90ms 就说明 1€ 拖了） |

第一项和第二项是关键：以前我靠「觉得」判断你怎么动，现在有数。

### 11.6 顺带把「66Hz」这个谎修了

现在手柄页单独按 10ms 采样，发包同频。

但**别再拿标称值自我安慰**：真正的空中速率还受 BLE 连接间隔限制（macOS 常见 15ms），
所以以录制日志里 `analyze_log.js` 报的 Hz 为准。这个数是可验证的，66Hz 那个不是。

### 11.7 握法改成横握

右手大拇指落在 K2 上，横屏 240×135 重排。屏幕到底该转 1 还是转 3，取决于设备
哪一面对着掌心 —— 代码猜不出来，所以**长按 K2 循环切**，按到正的为止。

## 十二、v0.9.1：发烫排查——我猜错了三次

作者说：「我发现现在这个 stick S3 容易发烫。」

这一章值得完整写下来，**因为结论不是「找到了某个 bug」，而是「我一开始的排查方法就是错的」**。

### 12.1 先给板子装了个温度计

ESP32-S3 有内置温度传感器，`temperatureRead()` 即可。日志里加了三个数：

```
tp=44.3/46.3   ← 芯片结温 / 本次开机峰值
mhz=80         ← 当前 CPU 频率（验证降频真的生效）
hz=18          ← 上一秒实际 notify 次数（验证按需发包真的生效）
```

**为什么一定要加 `mhz` 和 `hz`**：这两个数字是「我以为改了」和「真的改了」之间的唯一区别。
本项目已经吃过一次亏 —— v0.8 的固件注释写着「66Hz」，实际 loop 每 20ms 才转一圈，
标称值从来没兑现过。

### 12.2 改之前，先把能省的省掉

| 改动 | 依据 |
|---|---|
| 手柄页按需发包：手不动 50ms / 动 15ms | BLE 实际空中速率受连接间隔限制（macOS 常见 15ms），比它快只是排队，radio 一直开着 |
| BLE 发射功率降到 0dBm | 手柄离电脑 30cm，满功率是给穿墙准备的 |
| 屏保 CPU 240 → 80MHz | 屏保是插电常亮几小时的状态，16fps 慢动画不需要 240 |
| 手柄页 CPU 240 → 80MHz + 背光压 MID | 见下 |
| 手柄页刷新 25 → 15fps | 只画「挡板在哪」，不是动画 |

顺带修了两个真 bug：

1. **`leaveSaver()` 不恢复 CPU 频率。** 屏保降到 80MHz 后，退出时没人把它抬回 240 ——
   因为 `wakeScreen()` 只在 `!screenOn` 分支里设频率，而屏保期间 `screenOn` 一直是 true。
   漏了这句，退出屏保后整机卡在 80MHz，表现成「有时候慢有时候不慢」，极难复现。
2. **手柄页 `[ui] lifted -> wake` 50 秒刷 959 行。** 玩的时候手一直在动、姿态每刻在变，
   「被拿起」反复触发。这两页本来就不熄屏，处理它纯属白烧 CPU 和串口带宽。
   改法是拨开 `SCR_PAD` / `SCR_MAZE`，但**仍然调用 `takeLifted()` 把标志吃掉** ——
   否则标志会挂着，等翻回主界面时突然弹一次唤醒，看起来像幽灵事件。

### 12.3 然后实测数据打了我的脸

| 时刻 | 场景 | CPU | 屏 | BLE | 芯片温度 |
|---|---|---|---|---|---|
| 20:05 | 屏保 45s（**刚开机**） | 80 | 亮 16fps | 断 | **33.3** |
| 20:08 | 手柄页 50s | 240 | 亮 25fps | 广播→连 | 37.3 → 43.3 |
| 20:16 | 手柄页 75s | 240 | 亮 | 连 | **46.3** |
| 20:26 | 手柄页 200s（新固件） | **80** | 亮 bl=80 | 连 | 43.3 → 44.3 |
| 20:47 | 手柄页熄屏 5.5min | **80** | **关** | **断** | 45.3 → **44.3** |
| 20:53 | 关充电 5min | 80 | 关 | 断 | 44.3 → 43.3 |
| 21:00 | 屏保 40s（**已热**） | 80 | 亮 16fps | 断 | **44.3** |

最后一行和第一行**是同一个场景**：屏保、80MHz、无 BLE。差了 11°C。

**这就是全部答案：温度不取决于「现在在干什么」，取决于「过去一小时干了什么」。**

屏幕关、CPU 降到 80、BLE 断开、连充电都关掉，5.5 分钟只降了 1°C。
StickS3 是一根手指粗的封闭小棒，**热时间常数估计在 20 分钟以上** —— 热量进得去、出不来。

作者体感的「容易发烫」，本质不是某一项功耗高，而是**累积，且散不出去**。

### 12.4 我错在哪

我一开始拿「屏保 33.3」和「手柄页 46.3」对比，得出「CPU 频率是主因」，于是去改 CPU 频率。

但那个 33.3 是**刚开机 45 秒**测的，46.3 是**累积半小时**之后测的。**两个数根本不同基线。**

于是改完 CPU 频率，温度纹丝不动（46.3 → 43.3），我才发现自己一直在测「同一个热物体的不同部位」。

> 这是本项目**第二次**犯「用一个数字说圆自己编的故事」。
> 第一次是 v0.5.5 把 PM1 的 GPIO2 当成 CHG_STAT，读到 0/1 变化就宣布「确认在充电」，
> 结果是 LCD 电源闸，把屏幕弄黑了。

教训写在这儿：**做对照实验，必须先确认两组数据的基线一致。**
温度这种有惯性的量，没有「回到基线」就不能比。

### 12.5 那这些改动还有意义吗

有，但**不能靠短期测温证明**。

热惯性大 = 短期测温信噪比极低。真正能看出效果的是：

- **长时间运行后的稳态温度**（几小时尺度）
- **电池续航**（同等电量的使用时长）

降低的是**持续功耗**，而屏保是「插电常亮几小时」的状态，正是持续功耗占大头的地方。
CPU 240 → 80MHz 这一刀对屏保尤其有效（历史实测屏保常亮约 60mA）。

所以我不会再拿「改了之后温度降了 0.5°C」当证据 —— 那是噪声。

### 12.6 还给不出结论的部分

1. **`temperatureRead()` 有没有系统偏移，我没验证。**
   开机瞬间读到 35.3，如果环境 25°C，那芯片比环境高 10°C（启动时确实会热）。
   但也不能排除传感器本身偏 +5~10。**在没有外部温度计做基准之前，绝对值只能当参考，看相对变化。**
2. **背光 150 → 80，温度毫无变化 —— 我怀疑 `setBrightness` 在这块屏上没真正生效。**
   需要作者看一眼：手柄页的屏幕，比主界面暗吗？
   如果没暗，那背光这条优化是假的，我得直接去动 PM1 / 屏幕 IC 的背光寄存器。
3. **M5PM1 的 `setChargeCurrent()` 是个空函数**（`return false;`），
   所以充电电流软件改不了。唯一的旋钮是 GPIO3（CHG_PROG，低=大电流 / 浮空=小电流），
   而历史实测「换档不改变结果」，所以没动它。

### 12.7 三条实用建议

1. **「温」和「烫」是两件事。** 芯片 45°C 时机身表面大约 38~41°C —— 摸起来明显热，
   但离「烫手」还有距离。锂电池**烫到不敢碰**（>50°C 机身）才是要停用的信号。
2. **想立刻凉下来，只能断电。** 拔掉 USB 放十分钟，比任何软件设置都有效。
   插着 USB 时充电 IC 一直在工作，那是一个独立的、软件关不掉的热源。
3. **长期最有效的两个动作**：把亮度设成「中」（如果背光调光真的生效），
   以及别长时间连续玩 —— 手柄页是这台机器唯一「高频 + 无线电 + 常亮屏」同时在线的状态。
